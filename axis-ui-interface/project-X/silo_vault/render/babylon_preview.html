    NEXXUS Architecture Reference Manual
    

    

    









    

    


    

    Overview
    

    NEXXUS is a local-first control room: one dashboard, one server, and 21 independent engines that run as separate processes and answer a common contract. Nothing needs the internet to run, and no model decides which engine talks to which: routing is deterministic.
    

    LayerRole
    

    Control planepython_server.py: the single HTTP surface for the dashboard, chat, jobs and mesh routes.
    

    MeshHub plus 21 engines, each a closed silo, reached with signed, stateless calls.
    

    axis gateSigned manifests, replay protection, single-use tickets and drift detection for trusted files.
    

    DashboardThis page, served locally, with its 3D library bundled.
    

    Honest status: "operational" means an engine's own tests pass. See ENGINE_STATUS.md and AUDIT.md for what is not proven.
    

    


    

    Grid Controller (SRC Governor)
    

    The governing layer that decides what may run and where it goes. In this codebase it is the control-plane server, the deterministic router and the Build Governor working together. "Grid Controller" and "SRC Governor" are the project's umbrella names; the working pieces are listed below.
    

    Parts
    

    • Control plane (python_server.py): receives every command and dispatches it. Mode gates stop a command that does not belong to the current operating mode.
      • 

    • Build Governor (axis-logic/operations/build_governor.py): decides whether a build command may run. Only operations on its allow-list run; restricted commands are refused even if someone adds them to the allow-list.
      • 

    • Strict mode: data must be a plain object with no secret-looking keys (password, token, api key and similar) and no path tricks.
      • 

    • Fail closed: a missing or unreadable rule file means nothing is allowed.
      • 

    • Orchestrator bus (ORCHESTRATOR_BUS.md): signed order envelopes with fixed states ORDERED, ACKED, BUILT, QC_PASSED, ACCEPTED. The reviewer is never the builder, and only NEXXUS accepts.
    

    Operator limits
    

    Anything that adds capability, runs outside the sandbox or changes a trusted file waits for the owner's explicit approval. Operator-mode file access is limited to folders the owner grants (operator_scope.py); screen and camera capture are off until switched on (capture.py).
    

    


    

    AXIS Validator Engine
    

    The axis-validator silo is one of the 21 engines. Its code is a set of validation modules plus the shared engine files (health_report.py, mesh.py, live_status.py). In the engine status table it is marked operational: all of its source modules import and its tests pass.
    

    The definition of done for every engine
    

    • Every engine is run against a nine-point checklist (engine_checklist.py) and the raw output is dated, not summarised as "it works".
      • 

    • Each engine answers the mesh contract: health, ping, message and instruct.
      • 

    • A failed check reports ok: false in plain words. Nothing is swallowed.
      • 

    • Run the whole suite with python verify_all.py; it ends with ALL GREEN only when every suite passes.
    

    


    

    AXIS-Bridge
    

    The connection layer between the NEXXUS server and the engines. It is built so that each engine stays a closed silo.
    

    • Roster, not scanning: the bridge publishes mesh_roster.json (engine name to entry file). The server reads the roster and never opens the silo folders itself.
      • 

    • Process isolation: engine code is never imported into the server. Health checks and instructions run the engine's entry file as a separate subprocess with a timeout; only JSON crosses the boundary.
      • 

    • Opt-in: an engine takes part only if it declares the mesh protocol and handles --mesh.
      • 

    • Signed heartbeats: each engine signs with its own derived key; a bad signature is refused, logged and quarantined, never executed.
      • 

    • Two keys, kept apart: the governance secret (server and engines) and the admin token (typed into the dashboard for overrides).
      • 

    • Phone access: off by default. When on, it is reached over Tailscale with an admin token and no cross-site calls.
    

    The bridge and utility code is kept private; the public repository lists module names only (PRIVATE_MODULES.md).
    

    


    

    Scrapy pipelines
    

    Web crawling in NEXXUS runs through Scrapy, driven from the axis-search_engine silo. A small bridge component (web_crawling_nexxus.py) starts a Scrapy CrawlerProcess with the NEXXUS spider and its crawl configuration, so the search engine and the crawling layer stay separate.
    

    • Untrusted by default: crawled text is treated as data. Instruction-like text is scrubbed, results are cut short, and web search sends only the query text.
      • 

    • Switchable: hub web search can be turned off with NEXXUS_PORTAL_WEB_SEARCH=0.
      • 

    • Offline-safe: the engine is tested offline; search queries are URL-encoded and every component loads without a network.
      • 

    • Intake: tools found on the web are staged, never executed, briefed to you, and integrated only after owner approval.
    

    


    

    Local model router
    

    llm_router.py picks which local Ollama model NEXXUS uses, based on the operating mode. Everything is free and local: the standard library plus a local Ollama.
    

    ModeModel (default)Context
    

    Conversationphi4-mini (NEXXUS_CHAT_MODEL)2048 (NEXXUS_CHAT_CTX)
    

    Any build modeqwen2.5-coder:3b (NEXXUS_BUILD_MODEL)8192 (NEXXUS_BUILD_CTX)
    

    • Only one model is kept loaded at a time, which is what lets it fit in about 8 GB.
      • 

    • On a mode change the old model is unloaded and the new one preloaded in the background; the switch itself is instant, a cold load can take minutes on a small machine.
      • 

    • Chat uses the build model while a build mode is active, so there is no model swap mid-build.
      • 

    • If Ollama is down, callers get an honest error message, never a silent success. Server address: NEXXUS_OLLAMA_URL (default http://127.0.0.1:11434).
      • 

    • The context guard (context_guard.py) watches chat weight and prepares a handoff and continuation prompt before the small context window overflows.
    

    


    

    PICTHIS Studio
    

    picthis is an external module, kept in its own repository and connected through the module gateway with a hostname route. It is the 3D, animation and sound studio.
    

    • Photo to 3D: uses the InstantMesh model (TencentARC) for image-to-3D.
      • 

    • Animation and sound: motion is authored, not AI-generated. Models built without a photo are stylised.
      • 

    • Staging: image tools, working copies and a send menu run through the staging area; a dry run comes before anything is exported.
      • 

    • Connection: a one-line <name>.module.json pointer file in the UI folder names the module's folder; the gateway then treats it like any module.
    

    


    

    Telemetry panels
    

    • Server status (top-left): whether the Python server is active.
      • 

    • Engine LED strip (top bar): one light per engine; green answering, red offline, amber building.
      • 

    • Boiler Room (Diagnostic mode): a live monitor of every engine, the bridge and the infrastructure, refreshed every 2 seconds, with drill-down per engine and a conversation locked to the system (BOILER_ROOM.md).
      • 

    • AXIS LINK (Link mode): the backend window with a Transmission log of everything moving through the machine, click-to-inspect route playback and a two-slot input queue (AXIS_LINK.md).
      • 

    • Perimeter (control dock): the axis gate board with Hard Lock and Quarantine overrides, and breach alerts (PERIMETER.md).
      • 

    • Notifications (top-right bell): events needing attention.
    

    Telemetry stays on your machine. Nothing is sent out by default.
